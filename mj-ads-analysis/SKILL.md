# MJ 广告周度分析

核心原则：**广告数据变差不一定是广告的问题。** 先证明或排除广告以外的原因，再动广告。
每个结论都要能回答三件事：和上周比变了什么、和近几周基准比变了什么、原因是广告内部还是外部。

诊断规则和阈值全在 `references/rules.md`（向用户解释口径时读它）；拉数清单和参数在 `references/data-pulls.md`。

## 约定

- `SKILL` = 本 skill 目录；`RUN` = scratchpad 下新建 `ads/<产品代码>/<运行日期>/`。
- 时间：“最新一周” = 上一个完整的周一到周日。基准期 = 再往前 3–4 周，**剔除大促周**（Prime Day、Prime Big Deal Days、黑五网一）和大促后第一周单独看。
- 时间窗口：“近 7 天” = 昨天往前 7 天（领星当天数据通常还没有，先用 `get_sp_campaign_hour_data` 查今天是否有数），对比再往前 7 天。
- 批量拉数按全局规则走 batch-offload（`oc_pull.sh`）。DeepSeek 不通（如 `FreeUsageLimitError`）时，领星和三方的只读查询交给 agy（见 data-pulls.md 末尾），都不通时 Claude 自己调；大返回会自动落盘，只用 Python 读统计，不把全量读进上下文。在结果里用一句话说明分流情况。
- 西柚 `user_task` 填用户这次的原话；单次 4–7 Credits 的工具（价格趋势、排名趋势）只对主力 ASIN 和关键词调用。
- 判断、归因、调整计划由 Claude 做；脚本只算数。

## 第 -1 步：读上周的建议，用数据推断用户执行了哪些（有跟踪表时必做）

1. 读 `SKILL/data/<产品>/config.json`。有 `tracking_sheet` 就用 lark-cli `+csv-get` 读上一周的行（建议动作、当前设置）。
2. **用户不会填反馈，也不一定采纳建议（2026-10-26 用户要求）。** 对每条上周建议，用这周拉到的数据推断执行情况：
   - 出价：投放词报表的 `bid` 和上周记录的出价比；广告位加价：活动报表的 `placement_top`/`placement_product_page`；
   - 暂停/重开：活动 `state`，以及这周有没有花费；预算/分时：`daily_budget`、`is_apply_time`；
   - 否词/收词：投放词报表里有没有新增的精确词；否词看来源活动里该搜索词这周是否还有花费（有花费说明没否）。
   推断结果写成：已执行 / 部分执行 / 未执行 / 做了别的调整（写出具体变化），拿不准的写“无法判断”并说明原因。
3. 新一周的建议要基于**用户实际做了的状态**来给，不要假设上周建议已经执行。已执行的，评估效果（和执行前对比）；未执行的，如果这周数据仍支持就再提，并说明为什么，不支持就撤回。
4. 检查 `pending_reopen`：条件满足（如优惠券已恢复）就提醒用户重开，给出重开出价。

## 第 0 步：确认范围（不要信名字）

1. 领星 `ad_auth_shops` 拿 profile_id；`ad_campaign_report`（用 `name` 或 `portfolio_id` 筛选）找到该产品的活动。
2. 用 `ad_campaign_product_report`（按 portfolio_id）核对每个组合实际推的 ASIN/SKU。**组合名或活动名带产品代码不代表推的就是它**（例：“广告经理建议0416 GF2 3 AB10”实际推 GF3 和 AB10）。
3. 共享活动（如 SBPC 同时推多个产品）单独列出，不算进本产品主表，注明单均价判断主要出单的是哪个产品。
4. 记下产品的 ASIN 列表、售价、主力 ASIN、目标 ACoS（问用户或按领星毛利估算，见 rules.md §5）。

## 第 1 步：先看全局（商品层面，非广告）

拉 data-pulls.md 的 A 组，逐周（最新周 + 基准 3–4 周）列出主力 ASIN：
总订单、销量、Sessions、整体转化率、自然订单、广告订单、TACoS、每件销售额、促销订单数和促销折扣、可售库存和可售天数、星级和评论数、购物车相关字段、小类排名。

然后西柚：`get_asin_info_trends`（价格、优惠券、Deal、划线价逐日）、`get_asin_info_change_trends`（标题主图）、`get_asin_traffic_trends_weekly`（自然/广告各位置流量）、`get_asin_bsr_trends`。

按 rules.md §1 的清单逐项判定“有变化 / 无变化 / 无法判断”，写进报告的“非广告因素”一节。**重点检查价格口径陷阱**（rules.md §2）：优惠券开关会让报表里的广告销售额按不同价格记账，ACoS 会被放大或缩小。

## 第 2 步：广告整体对比

活动报表按周拉（最新周、上周，必要时基准各周）。分 SP/SB/SBV/SD、分组合汇总：花费、销售额、订单、点击、CPC、CTR、CVR、ACoS、CPA、单均价。
同时看 **订单数和 CPA**，不能只看 ACoS 和销售额（rules.md §2）。注意归因延迟：最近 2–3 天数据不全。

## 第 3 步：丢单词分析（必须做）

1. 拉近 5 周搜索词（按组合、`group_type=query`，每周一个文件），运行：
   `python3 SKILL/scripts/st_weekly.py --weeks W1 ... W5 --labels ... --exclude-baseline <大促周序号> --core <核心词...> --out RUN/st_weekly.json`
   注意：搜索词按 query 聚合时会把同一组合里不同产品的单混在一起，用单均价判断（单均价明显低的单多半是别的产品）。
2. 对每个丢单/下滑词（和花费最大的 5 个核心词），按 rules.md §3 的顺序逐项查原因：
   搜索量（ABA）→ 我方排名（自然位、SP 位，`get_asin_keyword_rank_trends`）→ 竞品（`get_keyword_asin_analysis`：价格、新进入者、广告流量增速）→ 自家其他链接是否在同词抢位 → 我方投放变化（暂停、出价、预算、分时、否词）→ 价格/优惠券变化。
3. 每个词给出结论：属于“需求变了 / 排名丢了 / 被竞品抢了 / 自家互抢 / 自己改了投放 / 价格竞争力变了 / 随机波动（量太小）”，再给对应动作。

## 第 4 步：逐个活动诊断

拉 data-pulls.md 的 C 组（按组合拉投放词和投放 ASIN 的周报；每个有花费的活动 14 天搜索词；SP 小时数据）。
运行或手写 digest：每个活动列本周/上周/14 天的 KPI、竞价策略、广告位加价、搜索结果顶部展示份额、分时策略、投放词（出价、本周/上周表现）、14 天前 6 个搜索词、否词候选。
另外按组合拉 30 天、60 天的活动报表（`ad_campaign_report`，report_date 写 30/60 天范围）。
判定用 rules.md §4：**14 / 30 / 60 天三档一起看**，单周只做参考。任何“暂停 / 否定”建议都要先过 §4 的三关（点击样本够不够、长周期好不好、是不是小花费长期达标），并在表里写出 30 天和 60 天的数。

## 第 5 步：输出

开头先写结论：变差的主要原因有几成是外部（价格、优惠券、竞品、需求、大促回落），几成是广告本身。然后：
1. 非广告因素表（证据 + 数据来源 + 建议，如恢复优惠券、调价，交给用户决定）
2. 丢单词表（词、5 周订单、原因、动作）
3. 逐个活动调整表：**每个活动一行，写活动全名，不许合并或缩写**（不能写“另外 3 个 SBV 小活动”“其余几个”这类话，2026-10-26 用户明确要求）。
   每行列：活动全名、类型、本周/上周 花费·订单·ACoS、14/30/60 天 花费·点击·订单·ACoS、现在的出价和广告位加价、判断依据（过了 rules.md §4 哪几关）、具体动作（改成多少）。
   所有在投活动都要出现，分“要动 / 暂停 / 保持”三组；已暂停但 60 天达标的活动单独列“建议重开测试”，同样写全名。
   出价和设置以本次拉数时的当前值为准，和上次拉数比较，有人改过的要写出来（例：顶部加价 125%→30%）。
   “标记”列用：⏸ 暂停·降价后再开 / 🟠 预警·需你判断 / ⬆ 加价 / ⭐ 增投覆盖 / 🔄 重开测试（规则见 rules.md §4、§4b）。表现好的活动不动，写“⭐ 增投覆盖”建议。
4. 高危预警（rules.md §4b）：`python3 SKILL/scripts/risk_flags.py --cur --prev --d30 --d60 --target` 出活动层级分档（⏸ / 🟠 / ⛔），🟠 只列数据模糊、需要用户判断的活动，写综合数据和二选一方案。没有就写“无”。
   否词涉及场景、材质类词根时，先跑 `scripts/root_stats.py` 看词根在各活动的表现（rules.md §4 否词部分）。
   提否词前按 rules.md §4c 复核：多周期数据、西柚看词下的意图和价格带、同价位头部竞品有没有降价，每个否词写出这几项再下结论。
5. 否词、收词、增投清单（否词只认两种理由；收词先查 60–90 天历史、排除品牌词；增投写清出单词、广告形式、目标活动、出价、依据）
6. 哪些能在领星直接写（`advertising_add_negative_keywords`、`advertising_add_negative_targets`、`advertising_sp_add_keywords`），哪些要手动改（出价、广告位、暂停、预算、分时）

### 写入飞书跟踪表

结果写进 config 里的 `tracking_sheet`（没有就用 lark-cli `+workbook-create` 新建“<产品> 周度广告调整建议”，并把链接和 token 存进 config）：
- 子表“活动调整建议”：每个活动一行，列为 周次、分组、活动全名、类型、状态、本周花费、本周订单、本周/上周/14/30/60 天 ACoS、14 天点击和订单、当前设置、判断依据、建议动作、标记。从第二周起在末尾加一列“上周建议执行情况（据数据推断）”。
- 子表“否词·收词·增投”：周次、类型、词、所在活动、匹配方式、建议出价/方式、理由；第二周起加“上周执行情况（据数据推断）”。
- **不留给用户填写的列**（用户不填，执行情况由第 -1 步推断）。每周在表尾追加新周次的行，不覆盖旧行。 ACoS 存成小数并设 `0%` 格式；冻结首行和前 3 列，加筛选。写完用 `+csv-get` 回读首尾几行核对。生成写入数据的脚本可参考 `data/GF2/` build_sheet_2026-10-26.py（数据 → `--sheets` JSON + `--styles` JSON）。

上一轮结论如果被新证据推翻（比如把分时策略误判成预算不足、把别的产品的单算进来），在报告里明确更正。

## 写入规则

- 默认只读、只出草案。领星写入（否词、加词）必须先把完整清单给用户确认，用户说可以才写，写完读回核对。
- 不交给子 agent 或 DeepSeek 做任何领星写入。
- 2026-11-03 实测：领星 MCP 写入工具返回 403“无权限调用该工具，请联系管理员开通MCP write 权限”。遇到 403 不重试，告诉用户要在领星开通 MCP 写权限，或把清单交给用户在后台手动改。
