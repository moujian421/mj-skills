# MJ-Listing 撰写

## 目标

把 Listing 撰写和优化做成一条可复核的决策链：以当前官方规则和真实商品事实为闸门，用查询、点击、转化与售后证据定位问题，产出可直接审核的文案和创意 Brief，再通过受控实验验证。不要把“写得好看”或“塞入更多关键词”当成完成标准。

## MJ 团队规则（优先于下文通用流程）

以下规则来自团队实际撰写时的明确要求；和下文通用流程冲突时，以本节为准。执行中的技术细节见 [references/execution-tips.md](references/execution-tips.md)。

### A. 规则与资料

1. **每次撰写前联网核对最新规则。** 至少核对标题、Item highlights、五点、后台词的字符上限和格式，写明来源链接与核对日期。2026-07-27 起非媒体类目：标题 ≤75 字符；Item highlights 是**一个**逗号分隔短语字段，≤125 字符，与标题合计 ≤200，和标题同等参与搜索（不是 5 条短句）；五点每条 10–254 字符，“短标题 + 冒号”，句尾不加标点。
2. **先找资料，再标缺证据。** 标 `NEEDS_EVIDENCE` 之前，依次查：本地产品文件夹（说明书、外箱标签、出货检验报告、工厂产品特点文档、展开/折叠尺寸图、样品照片）、样品讲解视频（先转写语音）、飞书聊天记录（按型号、工厂名、“参数/尺寸/材质/规格/轮”等搜索，并读相关文件和截图）、相关 wiki 表格。早期样品资料与最终配置冲突时，以最新的工厂/质检资料为准，并注明被取代的旧资料。用户问出处时，直接给原文、原图或视频截帧。
3. **用户或运营当面确认的事实算 A 级证据。** 来源写“用户确认 + 日期”（如 TPE 手柄、铝合金车架、手刹锁右后轮）。即使工厂资料只写了较笼统的说法（如“金属框架”），也按用户确认写入，但在审核表里保留工厂原文。

### B. 证据边界

4. **推断出来的说法不能当事实写。** 资料只描述了相邻事实时（例：说明书只写“按按钮装后轮”，不能写成 quick-release），要么找到直接证据，要么不写；不能把另一型号的证据套用过来。
5. **视频或口述里的配件，先结合画面确认作用对象。** 只看转写文字容易误判（例：讲解人说“用这个 hook 勾束另一边”，指的是球包托架弹力绳上的挂钩，用来绑球包，不是折叠后防散开的卡扣）。先截取对应时间的画面看清楚；仍不确定就问用户，不自己补功能。
6. **讲解人自己不确定的配置不写。** 讲解人说了“不知道是干嘛的 / 应该是 / 你调研一下”的项目（例：控制台里的“两个小球凹槽”），不进文案，审核表记为“待确认”。
7. **使用场景只写有出处的。** 配件的用途和场景只写资料或用户提到的，不自行扩展（例：不要给手机支架加“听音乐”）。
8. **不沿用与实物不符的旧模板。** 旧文案或模板里的配置（如 Foot Brake、Seat、Cooler）要逐项对照实物和资料，不符的直接删掉，并告诉用户。
9. **多型号逐个建事实表。** 同系列不同型号（如基础款/进阶款）的配置、轮径、重量、材质、折叠方式分开记录，不互相继承；某型号没有的配件不写进它的文案。

### C. 标题与 Item highlights

10. **用户指定的核心卖点必须进标题**（例：360° 前轮 + 手刹、一键折叠）。字数不够时按顺序处理：先删修饰词（如 Lockable）→ 再缩写词形（Folding→Fold、Hand Brake→Handbrake）→ 把次要信息挪到 Item highlights。核心品类词（如 3 Wheel、Golf Push Cart）不删。
11. **功能用词参照竞品标题。** 写标题前抓类目头部竞品的当前标题，看同一功能的常见说法（如 One-Click Folding、Handbrake、360° Front Wheels、3 Wheel），优先用买家熟悉的写法，并在备注写参照了哪个竞品。
12. **每个关键词都要可追溯，凑词放后台。** 标题和亮点里的词组要注明来自哪份关键词表、哪一行、搜索量多少。自己拼出来的短语（如 “Foldable Walking Bag Cart”）必须明说是拼的，不能当成现成关键词；查不到搜索量的说法注明“无搜索量，仅描述卖点”。标题和 Item highlights 只写真实卖点；纯为凑关键词的词（如 bag cart、walking cart、拼接短语）放后台搜索词（ST）。
13. **Item highlights 尽量填满 125 字符（目标 120–125），优先写买家能直接看到、摸到的卖点**：配件（手机架、杯架、伞架、记分卡盒、冰袋）、尺寸/轮径、重量、材质、手柄档位。空间不够时先缩短措辞（如 9.5/11.5 in wheels、cup and umbrella holder），再去掉五点里已讲清的次要项。
14. **规格数字用阿拉伯数字**（4-height，不写 four-height），即使通用规范建议一到九用英文单词。

### D. 卖点顺序

15. **先看竞品定骨架，同系列多型号用同一个顺序。** 抓 6–8 家头部竞品的标题和五点小标题，把每条归类（折叠、轮子、手柄/刹车、车架/重量、球包固定、收纳配件），算每类的平均位置，并看哪些配件出现在一半左右的竞品标题里（属于买家默认期待，如伞架）。
    - **五点：** 按平均位置定骨架（例：高尔夫推车 8 家竞品为前轮 1.7、折叠 2.0、手柄刹车 2.7、车架 3.9、球包固定 4.0、收纳配件 4.2），所有型号按同一顺序排；卖点多于 5 类时把相邻类合并成一条，不新增条数、不打乱顺序。
    - **Item highlights：** 接着标题没写的卖点往下排，所有型号用同一骨架，只把“型号独有配件”这一格换成各自内容；同一配件在各型号里写法一致；字数不够只删骨架末尾的项。
    - 把骨架和竞品依据写进文案表底。

### E. 交付与修改

16. **类目模板（PTD）不作为阻塞项。** 用户不要求时不读取 PTD，审核结论写“类目模板按用户要求不核对”，其余检查通过即可给 `READY FOR REVIEW`。运行审计脚本时在 `rules` 里设 `"ptd_waived": true`。
17. **交付格式。** 用中文和用户沟通。写入飞书表格：每个字段一行，列出英文文案、中文释义、字符数（后台词为 bytes）、上限、声明 ID、依据/备注；证据清单、声明账本、关键词映射、图片 Brief、实验卡另建一个审核 sheet。中文释义逐句对应英文，不增不减（不加“快速”“不回弹”这类英文里没有的说法）。写完回读关键单元格核对。
18. **改一处就全表搜一遍。** 任何修正都先在所有相关 sheet（竞品分析、样品档案、文案表、审核表等）里按中英文关键词搜同类说法（例：挂钩/hook、球槽/ball slot、music），一次改完，再回读确认没有残留；证据清单和声明账本同步更新。

## 不可妥协的边界

- 只写可追溯的事实。把未证实的材质、尺寸、兼容性、认证、功效、产地、质保和包装内容标为 `NEEDS_EVIDENCE`（先按 MJ 团队规则第 2 条找资料）。
- 不复制竞品文案、图片、商标或独特创意表达；只学习购买问题、信息顺序、功能常用说法和市场空白。
- 不把第三方估算、广告推荐词、AI 输出或一次前台观察写成 Amazon 一方事实。
- 只生成草稿，不直接改亚马逊后台；上传由用户在后台手动完成。
- 不用固定“20 次点击”“等 7 天”之类经验数作为通用阈值；根据流量、利润、归因窗口和统计证据定义样本与停止条件。
- 不把 Listing 与价格、优惠、库存、评论、配送或广告问题混为一谈；证据不足时保留多种解释。

## 先确定模式

在结果顶部声明一种模式：

1. `DRAFT`：撰写或改写字段级文案、创意 Brief 和证据缺口；默认模式。
2. `DIAGNOSE`：只读诊断已有 Listing，不改写完整内容。

## 核心工作流

### 1. 锁定对象和目标

记录 marketplace、ASIN、SKU、品牌、型号（多型号逐个记录）和本次主目标（新品撰写/合规/可发现性/CTR/CVR/预期管理，只选一个）。老品优化时再补充当前 Listing 快照、价格/优惠、库存、评分与评论量、广告和季节干扰。

若任务跨 ASIN 或变体，先建逐 SKU 事实矩阵。父体不得继承子体独有的颜色、尺寸、数量、图案或性能。

### 2. 核对最新规则

联网核对目标站点最新的标题、Item highlights、五点、后台词规则，记录来源和日期（MJ 团队规则第 1 条）。用户要求时才读取类目模板（Product Type Definition）；不读取时在审计输入里设 `"ptd_waived": true`。[references/official-policy.md](references/official-policy.md) 只作为基线，查到更新规则时以新规则为准。

### 3. 建立证据包

按优先级收集：

1. 商品实物、包装、说明书、外箱标签、出货检验报告、工厂资料、样品视频、检测/认证文件和用户确认；
2. Amazon 一方数据（老品）：Search Query Performance、业务报告、广告搜索词报告、退货原因和原始评论；
3. 目标站点当前搜索结果、类目节点和竞品页面观察（含竞品标题的功能写法）；
4. 卖家精灵、西柚等第三方估算，用于补充关键词搜索量、竞品曝光和评论样本；3 次以上或数据量大的查询按全局规则交给 batch-offload。

每条证据记录 `source / marketplace / ASIN-or-query / fetched_at / coverage / sample / limitations`。详细规则见 [references/evidence-and-experiments.md](references/evidence-and-experiments.md)。

### 4. 沿购物漏斗定位问题（可选：有流量数据的老品）

新品没有曝光、点击、转化数据时跳过本步，在审核表写“新品暂无数据”。有数据时先判定层级，再提出改动：

| 层级 | 主要信号 | 优先排除 | Listing 可能动作 |
|---|---|---|---|
| 资格与可售 | 抑制、缺货、Featured Offer | 价格/配送资格 | 修复属性、图片、变体或合规问题 |
| 可发现性 | query impressions、ASIN share、索引、类目/属性 | 需求弱、竞价/预算、类目错误 | 补全属性、重构查询覆盖 |
| 点击 | impressions → clicks、CTR | 展示位置、价格、评分、配送 | 主图、标题前段、变体缩略图 |
| 转化 | detail views/clicks → carts/orders、CVR | 价格、评论门槛、配送、流量错配 | 辅图、五点、描述/A+、视频 |
| 预期与售后 | 退货原因、差评主题、Q&A | 质量、履约、客服 | 明示尺寸/适配/限制/包装内容 |

输出“观察 → 证据 → 可能解释 → 排除项 → 建议动作 → 预期指标”。单一相关性不能证明因果。

### 5. 建立购买问题与声明证据矩阵

先回答消费者决策问题，再写文案。至少检查：

- 这是什么，适合谁/什么场景；
- 尺寸、适配、材质、容量、数量和包装内容；
- 如何使用、安装、清洁或维护；
- 与替代方案的真实差异；
- 限制、不适用情形和容易造成退货的预期差。

为每个拟写声明绑定 `claim_id → fact/evidence_id → 适用 SKU → 允许字段 → 风险级别`。没有证据 ID 的新增声明不得进入终稿。

### 6. 构建查询意图地图并改写

将查询按 `核心品类 / 属性规格 / 人群或对象 / 场景任务 / 问题收益 / 限制长尾 / 不相关 / 竞品品牌` 分类。先判断相关性和事实匹配，再决定位置：

- Title / Item Highlights：标题 ≤75 字符，放品牌、核心品类词和用户指定的核心卖点；Item highlights ≤125 字符，放标题装不下的差异信息，用逗号分隔短语，合计 ≤200。
- Bullets：按购买决策顺序，每条聚焦一个问题，采用“结论/收益 → 事实证明 → 适用边界”。
- Description/A+：补充解释、规格、比较、步骤、FAQ 和品牌价值；不要重复堆关键词。
- Backend：只放高度相关、前台未有效覆盖的通用同义词和本地表达；按 UTF-8 bytes 实算。
- Attributes：完整、准确填写必填与有购买价值的相关属性，和文案保持一致（如材质）。

高流量但不匹配商品事实的词必须排除；竞品品牌词只投广告，不进 Listing。

### 7. 产出创意系统，而非图片愿望清单

按 `品牌/商品事实 → 目标受众与购买任务 → 单一创意主张 → 信息层级 → 素材与模块` 推导。不要从某个大牌页面反向复制视觉风格。

区分主图与创意 Hero：主图必须先满足类目规则；生活方式 Hero 只用于允许的辅图、A+ 或品牌内容。每张素材只承担一个主要沟通任务，并给出：槽位、购买问题、核心信息、证据 ID、构图、必拍细节、禁用项、移动端要求和 alt text。

读取 [references/creative-and-conversion.md](references/creative-and-conversion.md) 生成完整创意 Brief、图片顺序、A+ 模块和移动端 QA。

### 8. 把 AI 限定为受控草稿工具

向 Amazon 或其它生成式 AI 仅提供事实矩阵、允许声明、目标语言、关键词候选和品牌语气。要求输出逐声明证据映射和不确定项，不要求“自由发挥”。

逐字段检查事实、语法、本地化、禁限词、商标、单位和变体一致性。AI 文案或 AI 场景图未经人工核对不得发布；AI 生成的场景不得改变商品结构、颜色、附件或包装内容。

### 9. 运行静态审计

把草稿整理成 JSON（字段格式可参考 [references/listing-input.example.json](references/listing-input.example.json)，示例仅供参考，可选）后运行：

```bash
python3 scripts/audit_listing.py listing.json --format markdown --fail-on hold
```

该脚本检查标题、Item highlights、五点、后台词、声明证据、主图元数据和创意槽位。它不能替代类目政策和图片人工审核。

### 10. 设计可解释的实验（可选：上线后有流量时）

- 需要因果诊断时，优先单属性实验并冻结价格、优惠、库存和广告主要变量。
- 只追求整体结果时，可使用 Manage Your Experiments 的多属性实验，但明确无法拆分各属性贡献。
- 优先使用 Amazon 的 “to significance” 或完整实验周期；不根据早期领先提前宣布赢家。
- 无 MYE 资格时采用前后分时版本，记录同期干扰并降低因果结论强度。
- 同时观察销售/CVR、单位访客、CTR、自然与广告订单、利润、退货和差评护栏。

不要在 Listing 实验期间同步修改广告 bid/placement/targeting；广告动作另建实验。

## 必须交付

按 [references/output-contract.md](references/output-contract.md) 输出。核心四块每次必交：

- 文案表：标题、Item highlights、五点、后台词的英文全文、中文释义、字符/byte 数、上限、声明 ID、依据；
- 证据清单与声明账本（含 `NEEDS_EVIDENCE` 和用户确认项）；
- 关键词映射（来源、搜索量、放在哪个字段）；
- 图片/A+/视频 Brief。

漏斗诊断、实验卡、广告联动、描述/A+ 正文和变体一致性按需输出。

最终状态只能是 `READY FOR REVIEW`、`DRAFT` 或 `HOLD`。`READY FOR REVIEW` 仍不等于已批准上传。
